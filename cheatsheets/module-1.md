# Module 1 on one page: Claude API Foundations for Architects

CCAR-F · the base of Domain 1, Agentic Architecture & Orchestration (27%), and a first step into Domain 5, Context Management & Reliability (15%) · Task Statements 1.1 and 5.1 (and 1.6, from Lesson 1.5) · checked against the Claude docs on 2026-10-14

| Lesson | Keep this |
|---|---|
| 1.1 How Claude reads a request | Text becomes tokens, and you pay for every token, in and out. The system prompt, every message, the tool definitions and the reply (thinking included) share one context window: 1M tokens on Claude Haiku 5.5. More room is not better reading: accuracy and recall degrade as the context grows. Count before you send; newer tokenizers give about 30% more tokens for the same text. The API is stateless: every request carries the whole conversation, so the bill grows turn by turn. The system prompt holds the role and the rules for every turn, the user turn holds this customer's words, and `max_tokens` is a ceiling on the output, thinking included, never a length setting. |
| 1.2 Reading the response | Read `content` by block `type`, never by position: `thinking` (on Haiku 5.5 its text comes back empty, with a signature, and it's billed as output), `text`, `tool_use`. `usage` is the receipt: input (the uncached part) plus cache writes and reads, and output, thinking included. Log the request ID (the `request-id` header; `_request_id` in the Python SDK). Decide the next step from `stop_reason`: `end_turn` use the answer; `tool_use` run the tool; `max_tokens` cut off, never ship it; `pause_turn` send the turn back as it is; `refusal` an HTTP 200 with no usable answer: discard it, read `stop_details.category`, and change the prompt rather than resend it. Keep the history append-only: Claude's turn goes back exactly as returned. |
| 1.3 Tool use from first principles | A tool is data: a `name`, a `description` Claude reads to decide when to call it, and an `input_schema` (JSON Schema). Claude sees the definition, never your code, and the definitions are billed as input on every request. Claude asks with a `tool_use` block (`id`, `name`, `input`); your code runs it and answers with a `tool_result` that carries the same `tool_use_id`, first in the next user turn, right after the call. Several calls in one response get all their results in one user turn. A failure still gets its result: `is_error: true` with an instructive message, so Claude can recover. |
| 1.4 The agentic loop | Send the request with the tools and the whole history; append Claude's turn as returned; run every `tool_use` block; send every result back in one user turn; repeat while `stop_reason` is `tool_use`; return the answer on `end_turn`. Any other stop reason is not an answer: handle it on purpose. A turn cap (`MAX_TURNS`, the SDK's `max_turns`) is a safety net, and hitting it is a failure. The three anti-patterns Task Statement 1.1 names: parsing natural language for "done", an arbitrary iteration cap as the main stop, and treating any text as completion. |
| 1.5 Who decides | If your code fixes the steps and their order, it's a workflow, even when it calls Claude at every step; if Claude picks its next action from what it has seen, it's an agent. Workflow patterns: prompt chaining (fixed steps, checks in code between them), routing (classify, then a specialized path), orchestrator-workers (a central model picks each input's subtasks: dynamic decomposition), plus parallelization and evaluator-optimizer. Climb one call → a workflow → an agent only when the rung below can't meet the requirement, and measure before you climb. |

## The five traps

| Trap | It sounds like | Why it's wrong |
|---|---|---|
| Make it bigger | "Use a larger model." "Move to a bigger context window." "Raise `max_tokens`." | Size fixes only a size problem. A bigger window is just as empty when the request leaves out the history, a bigger model reads the same broken request, and `max_tokens` is a ceiling, not a length. Read the evidence first: give it room when `stop_reason` says `max_tokens`. |
| Say it in the prompt | "Tell Claude to remember the order number." "Add a rule: finish within three tool calls." | A prompt line is a request, not a guarantee, and it can't add what the request leaves out. The API is stateless: send the whole conversation every time. A rule that must hold belongs in your code. |
| Read the words | "Stop when the reply says done." "Any text means it's finished." "Parse the decision with a regex." "Stop after three turns." | Wording changes from run to run, and text arrives right next to tool calls. Loop on `stop_reason`: continue on `tool_use`, finish on `end_turn`, handle anything else. A turn cap is only a safety net, and a decision you'd parse out of text belongs in a tool. |
| Retry it | "Retry the failed lookup." "Send the refused request again." | A retry fixes only what can pass on its own: dropped connections, rate limits, 5xx errors (the SDK already retries those, twice by default). A refusal, a bad input or a 400 won't pass on its own, and resent unchanged it usually fails the same way: fix the prompt or the request, or send the failure back as a `tool_result` with `is_error` and say what went wrong. |
| More machinery | "Make it an agent." "Add an orchestrator." "Replace the agent with a decision tree that covers every case." | Each changes more than the requirement asks. Start with the simplest design that meets it: one call, then a workflow, then an agent. Add complexity only when a measurement shows it pays. |
