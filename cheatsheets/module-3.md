# Module 3 on one page: Agents with the Claude Agent SDK

CCAR-F · Domain 1, Agentic Architecture & Orchestration (27%) and Domain 5, Context Management & Reliability (15%) · Task Statements 1.1, 1.4, 1.5, 1.7, 5.1 and 5.2 · Scenario 1 (Customer Support Resolution Agent), and Scenario 4 for sessions · checked against the Claude docs on 2026-10-16 · ⚑ marks a detail that is true today and may change

| Lesson | Keep this |
|---|---|
| 3.1 The Agent SDK from zero | The Agent SDK is Claude Code's agent loop as a library: `query()` runs the whole loop (Claude asks for a tool, the SDK runs it, the result goes back) until Claude stops asking. `ClaudeAgentOptions` sets the system prompt, the model, `tools` (the built-in tools; `[]` for none), `allowed_tools` (what runs without asking), `permission_mode` (`dontAsk`: not allowed means denied), `setting_sources`, and the safety nets `max_turns` and `max_budget_usd`. Your own Python functions become tools with `@tool` and `create_sdk_mcp_server`: an MCP server inside your app, its tools named `mcp__<server>__<tool>`. ⚑ The lessons pin `claude-agent-sdk==0.2.165`. |
| 3.2 The support agent and a target | Four tools: two that read (`get_customer`, `lookup_order`) and two that act (`process_refund`, `escalate_to_human`). The stream brings assistant messages (tool calls and text) and one `ResultMessage`: its `subtype` (how the loop ended: `success`, `error_max_turns`, …), the number of turns, the cost and the session ID. The subtype is not a grade. Measure first-contact resolution on labeled tickets: a resolve ticket passes with no escalation and exactly the expected refunds (from the backend's ledger, never from the reply), an escalate ticket passes if it reached a person (escalation recall), and wrong refunds are counted apart. Scenario 1's target: 80% or more. |
| 3.3 Enforcement, not instructions | A rule in the prompt is guidance: followed most of the time, so its failure rate isn't zero. When a step must hold every time (identity before an order is read or money moves), enforce it in code that runs on every call: a prerequisite gate in the tool's handler that remembers the customer `get_customer` verified for this case and refuses `lookup_order` / `process_refund` without one, or for someone else's order. The refusal is an error result Claude can read (`is_error`, a category and a reason), so the loop goes on and no data leaks. |
| 3.4 Hooks: intercept and normalize | A `PreToolUse` hook sees a call before it runs: return `permissionDecision: "deny"` with a `permissionDecisionReason` (refunds above $500: "call `escalate_to_human` instead; don't retry"). Hooks run before every other permission step, and a hook deny applies even in `bypassPermissions` mode. A `PostToolUse` hook sees a result before Claude does and can replace it (`updatedToolOutput`): one date format (UTC ISO 8601) and status names instead of codes. `HookMatcher(matcher=…, hooks=[…])`, passed as `hooks=` in the options. Choose a hook over a prompt when the business rule must hold. |
| 3.5 Escalation and ambiguity | Escalation is judgment, so it goes in the system prompt as explicit criteria with examples (3 to 5, with the reason for each): the customer asks for a person (hand over at once, without investigating first), the policy is silent or ambiguous on the request, or there's no progress. Not sentiment, not a self-rated confidence score. A frustrated customer with an in-scope issue: acknowledge it and offer the fix; escalate if they ask again. Several accounts match: ask for another identifier instead of guessing. |
| 3.6 Multi-concern requests and hand-offs | Split a message with several requests into items, look up what each needs (independent lookups can go in one turn), and answer all of them in one reply, with shared context such as the refund policy in the system prompt. A hand-off is for a person who never sees the transcript: make it a structured tool input with required fields (customer ID, order, root cause, amount, recommended action, summary), each described for its reader. |
| 3.7 Long conversations and case facts | Each summary of a summary blurs amounts, order numbers, dates and promises. Keep the transactional facts in a case-facts block outside the summarized history, filled from tool results (a `PostToolUse` hook), one entry per issue, and put it in every prompt. Trim tool results to the fields that matter before they pile up (12 fields to 8 in the lesson). A running summary is still fine for the gist. |
| 3.8 Sessions: resume, fork, or start fresh | A session is the whole conversation saved under an ID. Resume it to continue (`resume=` the ID in the SDK; `--resume <name>` or `-r` in Claude Code, after naming it with `-n`). Fork to compare two approaches from one baseline (`fork_session=True`, `--fork-session`): the fork gets a new ID and the original stays as it was; a fork branches the conversation, not the files. After files change, resume and say exactly which ones changed; when most of the context is stale, start a fresh session with a structured summary. |

## The six traps

| Trap | It sounds like | Why it's wrong, and the fix |
|---|---|---|
| Say it louder | "Write the rule in capitals." "Move it to the top of the prompt." "Add sample chats." "A prompt line to use only these tools." | Where a rule must hold every time, guidance has a non-zero failure rate: stronger wording lowers it, it doesn't make it zero. Put the rule in code that runs on every call: a gate in the handler, or a `PreToolUse` hook that denies with a reason. A prompt is still the right lever for judgment. |
| Trust a proxy | "Escalate when sentiment turns negative." "Escalate when the agent's confidence is below 7/10." "The customer sounds angry." | Sentiment measures mood, not complexity; self-rated confidence is least reliable on the hard cases. Write explicit criteria with examples (asks for a person, policy silent or ambiguous, no progress); acknowledge frustration and offer the fix; ask one question when several accounts match. |
| Count the wrong thing | "Count every `success` subtype as resolved." "The reply says it's resolved." "Raise `max_turns` so more runs finish." | The subtype says how the loop ended, not whether the case was handled right, and a reply is text, not an action. Grade each run against its label, from what the agent did (the ledger), and count escalations apart. |
| Ship the transcript | "Attach the whole chat to the hand-off." "Ask for longer summaries." "The customer can explain it again." | The person who takes over never sees the chat, and asking isn't guaranteeing. Required, structured hand-off fields: customer ID, order, root cause, amount, recommended action, each described for the reader. |
| Summarize harder | "Double the summary limit." "Use a bigger context window." "Tell it to double-check the numbers." | Every fold blurs amounts, orders and dates again. Keep case facts from the tool results outside the summary, one entry per issue, in every prompt, and trim tool results before they pile up. |
| Resume blindly | "Resume as it is." "Start a blank session and re-read everything." "Fork twice and see which one notices." | Resume trusts results that may be stale, a blank start throws away valid work, and forks compare approaches; they don't detect changes. Mostly still valid: resume and name the changed files. Mostly stale: a fresh session with a structured summary. |

Each of these moves is a real tool somewhere: a prompt for judgment, a running summary for the gist, resume when the context still holds, a transcript attached for an audit. It's wrong when it replaces what the question actually asks for.
