# Module 6 on one page: Claude Code in CI/CD

CCAR-F · Domain 3, Claude Code Configuration & Workflows (20%), and Domain 4, Prompt Engineering & Structured Output (20%), with Domain 1 (Agentic Architecture & Orchestration) · Task Statements 3.6, 4.1, 4.2, 4.4 and 4.6, plus 1.6 · Scenario 5 (Claude Code for Continuous Integration) · checked against the Claude docs on 2026-10-17 · ⚑ marks a detail that is true today and may change

**The one question:** what does the pipeline need to be sure of, and what makes it sure? Not a stronger word in the prompt, but a mechanism: a flag that exists, a schema, the earlier findings, explicit criteria, examples, a separate pass, an independent check, the tests you already have.

| Lesson | Keep this |
|---|---|
| 6.1 Claude Code without a human | `claude -p` (`--print`) runs once and exits: nothing waits for input, and the exit code tells the job whether it worked. Set permissions up front: `--allowedTools` for what may run, `--permission-mode dontAsk` to refuse the rest. `--output-format json` wraps the answer with metadata (turns, cost, session ID); add `--json-schema` and the data arrives in `structured_output`, in your shape. Plain `-p` loads `CLAUDE.md` and its imports; `--bare` loads none of it (no hooks, skills, MCP servers, memory or `CLAUDE.md`) and is the recommended mode for scripts ⚑; under `--bare` pass context in yourself (`--append-system-prompt-file` passes the file's text, not its `@` imports). A schema stops malformed output, not wrong findings. |
| 6.2 A pull request review pipeline | A workflow on `pull_request` (`opened`, `synchronize`: every push) runs the review script; the API key is a repository secret, the GitHub token comes from the job. Inline comments only on lines the diff shows; everything else goes in the summary. Pass the earlier findings into the next run: each finding is `new` or `still_open` (a required enum); fixed = earlier minus still open; post only what's new. |
| 6.3 Explicit criteria | Replace "be conservative" with categories to report (each defined) and to skip (style, naming, "consider" suggestions, anything not tied to one line); define each severity with an example from this codebase; keep a config switch to turn off a category that costs trust. Measure with repeated runs on the same diff. Our runs: the same line went from medium to high; a speculative finding still came back in one run. |
| 6.4 Few-shot for consistent output | Two to four examples, each a diff line and the exact finding it gets: the format, one root cause as one finding, and cases where the answer is None (acceptable code next to real issues). Make them diverse, and never copy the lines under review. Our runs: three then four findings without examples; the same two findings twice with them, and sensible findings on an unseen diff. |
| 6.5 Independent and multi-pass review | A session that wrote the code reviews its own reasoning; a fresh, independent instance sees only the diff and the criteria. Big changes: a pass per file for local issues, then one cross-file pass for what spans files; then a separate instance checks every finding (verdict + confidence). Confident findings go inline, the rest to a person (`inline_confidence` in config). Our run: the cents bug between two files, found by the cross-file pass, confirmed 0.97. |
| 6.6 Test generation that adds value | Test standards in the project's `CLAUDE.md` (read on every run). Give the prompt the existing tests and ask each new test for `why_new`; write to a new file, never overwrite, and run what you generate. Tag every finding with a `detected_pattern`, log dismissals, and tune the reviewer by the dismissal rate per pattern. Our runs: five tests, 5 passed, the suite 139 passed; `raw-order-dates-read` 1 of 1 dismissed. |

## The eight traps

| Trap | It sounds like | Why it's wrong, and the fix |
|---|---|---|
| Invent a flag | "Set CLAUDE_HEADLESS=true." "Add --batch." "Use --non-interactive." | None of these exist in Claude Code; a job that waits for input hangs. `claude -p`, with `--allowedTools` and `dontAsk` set up front. The Message Batches API is a different product, for a big job that can wait up to a day. |
| Assume the context | "CI ignores CLAUDE.md, so paste the rules into every prompt." "--bare is just a faster -p." | Plain `-p` loads `CLAUDE.md` and its imports; `--bare` loads none of it; `--append-system-prompt-file` passes text, not `@` imports. Know which mode the job runs; under `--bare`, pass the context in. |
| Parse the prose | "Grep the review for 'bug'." "Ask for a Markdown table and split the rows." | Prose changes shape from run to run. `--output-format json` + `--json-schema`; read `structured_output`; required fields, enums for severity and category. |
| Say it all again | "Re-run the full review on every push." "Review only when the PR opens." "Delete the bot's old comments first." | Re-posted fixed issues train developers to ignore the bot; one review misses later commits. Pass the earlier findings; mark each `new` or `still_open`; post only the new. |
| Just be careful | "Be conservative." "Only report high-confidence issues." "Be thorough." | Vague words move the noise, not the line. Categories to report and to skip, severity defined by examples, a switch for a noisy category. |
| Ask for consistency | "Tell it to be consistent." "Set the temperature to 0." "Merge nearby findings in a script." | Nothing defines what one finding looks like. Two to four examples: the exact finding, one root cause = one finding, cases where the answer is None. |
| One bigger pass | "Use a bigger context window." "Take the consensus of three runs." "Let the author's session review its own change." | More room isn't more attention; agreement isn't verification; the author shares its own assumptions. Per-file passes + a cross-file pass + an independent check with confidence for routing. |
| More tests | "Generate more tests per module." "Delete the generated tests that fail." "Keep the conventions in your own ~/.claude." | Volume duplicates; passing isn't coverage; a personal file never reaches CI. Standards in the project `CLAUDE.md`, the existing tests in the prompt with `why_new`, run what you generate, dismissal rates per `detected_pattern`. |

Each of these moves is a real tool somewhere: the Message Batches API for a job that can wait, a bigger context window when the input truly doesn't fit, repeated runs to measure drift (Lessons 6.3 and 6.4 did exactly that), `--bare` for scripts. It's wrong when it replaces what the question asks for.
