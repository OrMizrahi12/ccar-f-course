# Module 5 on one page: Configuring Claude Code for a Team

CCAR-F · Domain 3, Claude Code Configuration & Workflows (20%), with Domain 2 (Tool Design & MCP Integration) and Domain 5 (Context Management & Reliability) · Task Statements 3.1, 3.2, 3.3, 3.4 and 3.5, plus 2.4, 2.5 and 5.4 · Scenarios 2 (Code Generation with Claude Code) and 4 (Developer Productivity with Claude) · checked against the Claude docs on 2026-10-17 · ⚑ marks a detail that is true today and may change

**The one question:** who needs this, and when? Who: the whole team (commit it with the repository) or just me (keep it in my home folder or a gitignored file). When: every session, only for some files, or on demand.

| Lesson | Keep this |
|---|---|
| 5.1 Working with Claude Code | Explore, plan, code, commit. Plan mode reads and proposes; nothing is edited until you approve the plan. Pick the permission mode by risk: manual (`default`, reads only), accept edits, plan, auto (a classifier reviews actions); Shift+Tab cycles them ⚑. Deny rules block in every mode, including `bypassPermissions`. `/context` shows what fills the window, `/compact <focus>` replaces the conversation with a focused summary, `/clear` starts fresh between unrelated tasks, `/resume` picks up an earlier session. |
| 5.2 The CLAUDE.md hierarchy | `~/.claude/CLAUDE.md`: personal, every project, only you. Project `CLAUDE.md`: committed, every teammate gets it on the next pull. `CLAUDE.local.md`: personal for one project, kept out of git. A subdirectory's `CLAUDE.md` loads on demand, when Claude reads a file there (a `Loaded` line appears). Keep the project file short with `@path` imports (expanded at launch). Check with `/memory` and `/context` (Memory files). CLAUDE.md is context, not enforcement. A teammate missing your rules means they live somewhere git doesn't share. |
| 5.3 Rules and path-scoped conventions | `.claude/rules/*.md`: rules without `paths` load in every session; a rule with `paths:` globs (`"tests/**/*.py"`) loads when Claude reads, writes or edits a matching file. One rule beats copies of the same text in many folders' CLAUDE.md files; a folder with rules of its own can still have its own CLAUDE.md. |
| 5.4 Slash commands and skills | Commands (`.claude/commands/*.md`) have been merged into skills (`.claude/skills/<name>/SKILL.md`). Frontmatter: `description`, `argument-hint`, `allowed-tools` (no prompt for those tools during the turn), `context: fork` with `agent` (runs in a subagent that doesn't see your conversation; good for long output). CLAUDE.md for what every session needs; a skill for an occasional procedure (its body loads only when used). Project skills are committed; personal ones live in `~/.claude/skills/`, under their own name (a personal skill with the same name wins over the project's). |
| 5.5 Plan mode or direct execution | A diff you can describe in one sentence: do it directly. Many files, an open design, unfamiliar code or real risk: plan mode, with the Explore subagent for the discovery, then approve the plan. Our runs: `>` to `>=` fixed directly (3 passed, the suite passed); retiring a shim other code imports was planned first (Explore found the dependents). |
| 5.6 Iterative refinement | Let Claude interview you first; give 2 or 3 input → output examples; write the tests first and watch them fail; share the failing output, not "it's still wrong". Interacting issues in one message, independent ones one at a time. Our run: nine questions (one we hadn't thought of), 5 failed / 1 passed for the wrong reason, then 6 of 6 and the suite green. |
| 5.7 Exploring a large codebase | Signs of a crowded context: generic answers ("typical patterns"), forgotten specifics. Fix: Explore subagents per area, findings in a scratchpad file, `/compact` with a focus, the next phase starting from the file. `/clear` throws findings away, so keep it for unrelated tasks. |
| 5.8 A developer productivity agent | Agent SDK: built-in tools by name (Read, Grep, Glob, Write, Edit, Bash) plus an MCP server in `mcp_servers`; `setting_sources=[]`, `allowed_tools` (here only `Bash(.venv/bin/python -m pytest *)` for Bash), `permission_mode="dontAsk"` (anything else is refused, with no prompt), `max_budget_usd`. Tool descriptions say what the tool returns and when to use it instead of Grep (our run: `trace_export` first, 3 turns, no Grep). Verify the agent's claims yourself: a refused chained command meant it never ran its tests; the developer's suite run did (129 passed). |

## The eight traps

| Trap | It sounds like | Why it's wrong, and the fix |
|---|---|---|
| Keep it personal | "Put it in ~/.claude." "Each developer adds it to their own settings." "Add the server at user scope." | Nothing personal reaches a teammate's clone. Team rules in the project CLAUDE.md, `.claude/rules/` or `.claude/skills/`; team servers in `.mcp.json` with `${VAR}` for each developer's secret; all committed. Keep `~/.claude` for your own preferences. To block a command, use a deny rule: an instruction is not enforcement. |
| Invent a config file | ".claude/config.json." "Coding standards inside settings.json." "An instructions field in .mcp.json." | Claude Code reads instructions from CLAUDE.md files and their imports, `.claude/rules/` and skills. Settings files hold permissions and options; `.mcp.json` holds servers. Name the real file. |
| Wrong home for the knowledge | "A skill for always-on rules." "Paste the 300-line checklist into CLAUDE.md." "A command for the coding style." | CLAUDE.md and rules without `paths` load every session; a skill's body loads only when used. Always-needed rules in CLAUDE.md or a rule; an occasional procedure in a skill (forked when its output is long); a personal variant under its own name. |
| A CLAUDE.md in every folder | "Copy the testing rules into every folder's CLAUDE.md." "One CLAUDE.md per test directory." | Conventions spread across the tree would need many copies that drift. One `.claude/rules/` file with `paths:` globs, loaded when Claude reads or edits a matching file. |
| One way of working | "Always use plan mode to be safe." "Skip planning and review the diff afterwards." "Bypass permissions to go faster." | Planning a one-line fix wastes time; an unplanned multi-file change can break callers. Direct for a one-sentence diff; plan mode (with Explore) for many files, open designs or risk; the permission mode by risk, deny rules for what must never run. |
| Say it louder | "Describe the format in more detail." "Tell Claude it's still wrong." "Raise the effort level." | Prose leaves gaps Claude fills by guessing; "wrong" carries no information. An interview, 2 or 3 input → output examples, tests first, the failing output shared; interacting issues together. |
| One long conversation | "Keep going in the same session." "Ask Claude to be more specific." "/clear and ask again." | Context fills: answers turn generic, specifics are forgotten; `/clear` throws findings away. Explore subagents per area, a scratchpad file, `/compact <focus>`, a phase summary before the next phase; `/clear` between unrelated tasks. |
| Force the tool | "Remove Grep so the agent must use the MCP tool." "Tell it to prefer MCP tools in general." "bypassPermissions so it can run anything." | Without Grep the agent loses a tool it still needs; a vague preference names no tool for no question; opening every command to run one is too much. Descriptions that say what the tool returns and when to use it instead of Grep; `allowed_tools` with the exact test command under `dontAsk`; verify the agent's claims. |

Each of these moves is a real tool somewhere: `~/.claude/CLAUDE.md` for personal preferences, a skill for an occasional procedure, plan mode for a migration, `/clear` between unrelated tasks, removing a tool a role never needs. It's wrong when it replaces what the question asks for.
