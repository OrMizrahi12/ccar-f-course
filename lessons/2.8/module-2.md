# Module 2 on one page: Tool Design & MCP Integration

CCAR-F · Domain 2, Tool Design & MCP Integration (18%) · Task Statements 2.1 to 2.5 · a primary domain in Scenarios 1, 3 and 4 · checked against the Claude docs on 2026-10-15 · ⚑ marks a detail that is true today and may change

| Lesson | Keep this |
|---|---|
| 2.1 Tool descriptions that route | Claude picks a tool by reading the tool definitions it was sent; it never sees your code. The description is by far the most important factor: what the tool does and returns, when to use it, the input format, the edge cases, and the boundary (when not to use it, and what to use instead). The parameter lines tell the same story. Descriptions are billed as input on every request. Measure tool selection before and after a change, on labeled requests plus a held-out set labeled before you start. A description steers; a rule that must hold belongs in code. |
| 2.2 Rename, split, constrain | One distinct job per tool, with a name that says it. A generic tool (a mode switch and one free-text input) can't state what each job needs or returns. Same resource and same contract: consolidate, even into one tool with an `action` parameter. Different inputs or results: split, each with its own contract. Test every system-prompt line that names a tool: a line keyed to a word fires on the word and can override good descriptions; key it to the situation, or delete it. |
| 2.3 How many tools, and `tool_choice` | Every tool definition is input on every call, and every tool is one more option in every decision. Give each agent the tools its role needs; a tool it must not use is never offered. Past 30 to 50 tools, picking the right one degrades: use tool search. `tool_choice`: `auto` (the default with tools), `any`, a named `tool`, or `none`. Forced use (`any` or `tool`) returns only the tool call, with no text or thinking first. ⚑ Opus 5.5 and Sonnet 5.5 reject forced tool use with a 400: use `auto` with strict tool use, or structured outputs. |
| 2.4 Structured error responses | Flag a failure (`is_error` in the Messages API, `isError` in MCP) and say what failed: a category (transient, validation, business, permission), whether a retry can help (`isRetryable`), and a readable reason; for a policy refusal, `retriable: false` and a reason the agent can pass on. Claude picks its next move from what the result says. Retry only what can pass later, like a timeout. An empty result (`[]`) is a success, never an error; a failed lookup is not. |
| 2.5 MCP from zero | The host (the AI application) creates one MCP client per server. A server offers tools (the model calls them), resources (read-only data by URI, read by the application, such as a policy or a catalog that rarely changes) and prompts (templates the user picks). A stdio server talks on stdin and stdout, so it never prints to stdout. Test it in memory and in the MCP Inspector. |
| 2.6 MCP in Claude Code | Pick the scope by who should get the server: local (⚑ the default: private to you, in this project), project (`.mcp.json` at the repo root, committed; each developer approves its servers once), user (private to you, in every project). Keep secrets out of the shared file with `${VAR}` or `${VAR:-default}`, filled in from each developer's environment; an unset variable shows up as "Missing environment variables". Use an existing server for a standard system; build your own for yours. |
| 2.7 Built-in tools | Grep searches file contents (a name, an error, an import); Glob finds files by name pattern (`**/test_*.py`) and doesn't respect `.gitignore` by default. Read shows a file with line numbers. Edit replaces an exact string that must appear exactly once: add context for a unique anchor, or use `replace_all`; when Edit can't anchor, Read then Write. Explore step by step: search, read what matched, follow the names. ⚑ On macOS, Linux and WSL, Claude Code leaves Grep and Glob out of its default tool set and searches with Bash. |

## The six traps

| Trap | It sounds like | Why it's wrong |
|---|---|---|
| Say it in the prompt | "Add few-shot examples first." "Add a rule: when a customer mentions shipping, call `list_orders`." "Tell Claude to take extra care picking tools." | Claude picks a tool by reading the tool definitions, and a keyword rule fires on a word, not on the need: it can override a good description. Fix the description first, and reword a guilty prompt line by situation, or delete it. Examples are a real technique, just not the first fix. |
| Add a layer | "Put a routing classifier in front of the agent." "Add a step that picks the tool for each request." | It adds a component and a model call, and the weak tool behind it stays weak. Fix the tool itself, then measure it on requests it wasn't written around. A router can be the right design later; it's the wrong first step. |
| One tool for everything | "Merge them into one tool, so there's nothing to choose." "One tool with a mode switch and a free-text query." | When the input and the result change with the mode, no schema can say what each job needs or returns. Grouping related operations on one resource behind an `action` parameter is fine. Same contract: merge. Different contracts: split. |
| Give it everything | "Give every agent every tool, just to be safe." "Read every file first." | Every tool definition is input on every request, and every tool is one more option in every decision. Give each agent its role's tools, search before you read, and put a catalog that rarely changes in a resource. |
| Hide the failure | "Return 'Operation failed' for every error." "Return an empty list when access fails." "Retry on the server until it works." | Claude chooses its next move from what the result says. Flag the failure, name its category, say whether a retry can help, and add a readable message. An empty result is a success; a failed lookup is not. |
| Right idea, wrong place | "Put the token in `.mcp.json` so everyone has it." "Add my personal server in project scope." "Add the team's server in my user scope." | The setting is right; the file or the scope is wrong. Put a variable reference in the shared file, team servers in project scope, your own in user scope, and a private, one-repo setup in local scope. |
